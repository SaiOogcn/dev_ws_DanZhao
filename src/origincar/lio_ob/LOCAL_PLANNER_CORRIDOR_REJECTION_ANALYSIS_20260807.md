# lio_ob 局部避障“路径走廊全部拒绝”分析

日期：2026-08-07

## 1. 结论

本次停车的直接原因不是角速度超限、禁行区或雷达碰撞，而是局部规划器生成的 **17 条轨迹全部被“路径走廊”硬约束拒绝**。

日志：

```text
候选点=30
拒绝统计[
  角速度=0
  路径指标=0
  路径走廊=17
  禁行区=0
  碰撞=0
]
```

其中“候选点=30”这个日志名称容易误导。代码实际打印的是 `laser_points_.size()`，即经过聚类、确认、墙体/场界过滤和短期记忆后，当前参与计算的 **30 个激光障碍点**，不是30条候选路径。

当前参数实际生成的局部轨迹数为：

```text
15个均匀曲率样本
+ 1个纯追踪曲率
+ 1个视觉指令对应曲率
× 1个速度样本
= 17条轨迹
```

因此 `路径走廊=17` 和实际轨迹总数完全相等。结合其他拒绝计数均为0，可以确定：本轮17条轨迹全部在路径走廊检查处提前返回，没有任何一条进入最终候选集。

## 2. 为什么肉眼看起来有路，规划器却认为无路

### 2.1 规划器判断的是“是否靠近记录路径”，不是“地面上是否存在空地”

每条局部轨迹都会按 `0.05 m` 的步长向前推演，总推演距离为 `1.80 m`。每一个推演位姿都必须满足：

```text
预测位姿到当前可参考记录路径点的最近距离 <= 路径走廊宽度
```

当前启用了禁行区掩码，因此避障时直接使用：

```yaml
emergency_path_half_width: 1.05
```

只要一条轨迹中的任意一个推演点距离记录路径超过 `1.05 m`，整条轨迹立即作废。照片中存在物理通路，只能说明那块地面可能没有锥桶；它不代表该通路位于记录路径中心线的 `1.05 m` 范围内。

### 2.2 当前位置很可能位于扫码后 parking 路线的极短前进段

顺时针和逆时针 `parking` 路线开头相同：

```text
点1  (4.2000, 1.5000)  前进
点2  (4.2413, 1.5245)  前进
点3  (4.2587, 1.5355)  前进
点4  (4.3000, 1.5600)  前进
点5  (4.2141, 1.5142)  倒车
```

点1到点4的同方向路径总长只有约 `0.116 m`，点5立即切换为倒车。

`nearest_path_metric()` 为避免一条前进轨迹错误匹配到倒车路径，只从当前 `progress_index` 向前搜索到 **当前同方向段终点**。也就是说，当车辆还处在点1至点4时，局部避障轨迹只能参考这4个前进点，不能参考点5之后的倒车路线。

与此同时，局部规划器仍要求每条前进轨迹完整推演 `1.80 m`。这相当于：

```text
可参考的同方向路径只剩约0.116 m
但候选轨迹必须向前计算1.80 m
并且全程不能离这4个点超过1.05 m
```

这个组合非常容易让所有轨迹必然越界。它是本次 `路径走廊=17` 最可能、也最符合照片位置和路线结构的根因。

### 2.3 当前轨迹库不是任意自由空间规划

每条候选轨迹都是固定的三段曲率轮廓：

1. 前40%距离使用候选曲率转出；
2. 中间20%保持直行；
3. 后40%使用反向曲率尝试回到路径。

规划器不会生成任意折线、任意终点、原地调整或“先停车再按既定倒车段离开”的动作。即使人眼能看出一条通路，只要这条通路不属于17条固定曲率模板，规划器仍会报告无可行轨迹。

### 2.4 定位、路径进度错误会进一步放大走廊拒绝

路径距离使用 `/lio_ob/odom` 中的当前位姿，并且只搜索 `progress_index` 之后、当前同方向段内、`local_path_window=2.5 m` 范围的路径点。因此下列情况都会使路径走廊距离偏大：

- 扫码交接时实际停车位姿偏离设计接入点 `(4.20, 1.50)`；
- LIO存在横向漂移或航向误差；
- `progress_index` 已错误前跳，车辆身边的正确参考点位于索引之前；
- 当前路线文件或扫码方向选择错误；
- 路径与LIO坐标系的原点、旋转没有正确对齐。

但从“17条恰好全部走廊拒绝”和路线开头只有0.116 m前进段来看，短方向段与1.80 m推演距离的矛盾应排在定位误差之前。

## 3. 一条局部轨迹的硬拒绝标准

代码按以下顺序逐项检查。任何一项失败，整条轨迹立即返回无效，后面的检查不会继续执行。

| 检查顺序 | 日志项目 | 判定标准 | 当前关键参数 | 本次计数 | 解释 |
|---:|---|---|---|---:|---|
| 1 | 角速度 | `abs(speed × curvature) > max_yaw_rate` | 避障速度上限 `0.60 m/s`、最大曲率 `2.5 1/m`、最大角速度 `2.5 rad/s` | 0 | 最大采样角速度约 `1.5 rad/s`，没有超限 |
| 2 | 路径指标 | 在当前进度之后的同方向局部路径中找不到有限最近距离 | `local_path_window=2.5 m` | 0 | 找得到参考路径点，不代表距离足够近 |
| 3 | 路径走廊 | 任一推演点到最近参考路径点距离大于走廊半宽 | 避障时 `emergency_path_half_width=1.05 m` | 17 | 本次所有轨迹都在这里失败，是直接停车原因 |
| 4 | 禁行区 | 车体采样点进入禁行区，且本轮不允许借用禁行区 | 掩码阈值128；避障搜索当前允许借用禁行区 | 0 | 当前避障模式下通常不会作为硬拒绝，只会增加代价 |
| 5 | 碰撞 | 膨胀车体矩形与任一确认激光点重叠 | 半长 `0.14+0.16+0.04=0.34 m`；半宽 `0.10+0.16+0.04=0.30 m` | 0 | 只说明轨迹在被走廊拒绝前未触发碰撞，不能证明完整轨迹绝对无碰撞 |

拒绝统计是“第一个失败原因”的计数，不是五种条件互相独立的统计。例如某条轨迹后半段既越出走廊又会撞锥桶，但它先在走廊检查处返回，日志只会给“路径走廊”加1，碰撞不会加1。

## 4. 影响因素排序

### 4.1 针对本次故障的影响排序

1. **当前同方向路径剩余长度与局部推演距离不匹配**  
   parking路线开头前进段约0.116 m，而局部轨迹固定推演1.80 m；路径搜索又不能跨过前进/倒车换向点。这是最可能的根因。

2. **`emergency_path_half_width=1.05 m` 的硬走廊约束**  
   它直接淘汰了全部17条轨迹。放宽后可能出现有效轨迹，但单纯放宽也可能让车辆冲向场边或错误区域。

3. **扫码交接位姿、LIO误差和 `progress_index`**  
   当前位姿或路径进度一旦偏差，会让所有推演点计算出的最近路径距离整体增大。

4. **轨迹模板有限**  
   只有15个均匀曲率加追踪/视觉两条曲率，且全部是“转出—直行—转回”的固定结构，不包含提前换向、短距离动作和自由终点。

5. **`local_plan_horizon=1.80 m` 与 `local_plan_turn_fraction=0.40`**  
   推演越长、末端必须回归路径的要求越强，越容易在短路径段或换向点附近超出走廊。

6. **30个激光障碍记忆点**  
   它们负责触发避障并参与碰撞/间隙代价，但本次碰撞拒绝为0，所以不是17条轨迹失效的直接原因。30个点会保留约0.80 s，不能理解为30条路径。

7. **禁行区约束**  
   本次为0，且启用掩码时的主动避障允许短暂借用禁行区，所以禁行区主要作为软代价，不是当前硬拒绝来源。

8. **角速度限制**  
   本次为0，现有速度和曲率组合没有触及上限。

### 4.2 一般情况下的硬安全影响排序

如果不局限于本次日志，而按“对安全和可行性的通常影响”排列：

1. 碰撞包络与障碍点质量；
2. 路径走廊及路径/LIO对齐；
3. 同方向路径段、进度索引与推演范围；
4. 禁行区和场界标定；
5. 底盘最大曲率、角速度和真实转向响应；
6. 轨迹采样数量、速度样本和曲率分布；
7. 软代价权重。

这个排序与代码检查顺序不同。代码检查顺序只是为了尽快返回；安全影响排序描述的是哪个因素更容易改变真车结果。

## 5. 硬拒绝之后如何选择最优轨迹

只有通过全部硬检查的轨迹才会进入代价比较。当前主要软代价为：

| 代价项 | 配置权重 | 作用 |
|---|---:|---|
| 禁行区占比 | 80.0 | 强烈不鼓励车体进入黑区，但主动避障时不一定硬拒绝 |
| 末端返回路径 | 24.0 | 要求轨迹末端回到记录路径附近 |
| 贴合视觉转向命令 | 24.0 | 偏向视觉给出的避障方向和转向量 |
| 全程路径距离 | 18.0 | 偏向靠近记录路径的轨迹 |
| 首选绕行侧 | 10.0 | 惩罚走到指定绕行侧的反方向；属于软偏好，不是硬禁止 |
| 速度奖励 | 8.0 | 偏向较快轨迹；当前只有1个速度样本，基本不起区分作用 |
| 前向进度奖励 | 7.0 | 偏向沿记录路径取得更多进度 |
| 航向误差 | 2.0 | 偏向与记录路径航向一致 |
| 障碍间隙 | 0.9，且除以间隙 | 越接近障碍代价越大，距离很小时仍可能非常显著 |
| 转向变化 | 0.8 | 避免角速度突变 |

不同代价项单位不同，不能只按数字机械比较。特别是障碍间隙使用倒数形式，在距离很小时会迅速放大。但这些权重都无法挽救本次故障，因为17条轨迹在进入代价比较前已经全部被硬拒绝。

## 6. 建议的排查和优化优先级

### P0：先确认根因，不改变安全边界

复现时同步记录：

```bash
ros2 topic echo /lio_ob/state
ros2 topic echo /lio_ob/odom
ros2 topic echo /lio_ob/local_plan
ros2 topic echo /lio_ob/tracking_path
ros2 topic echo /lio_ob/obstacles
```

在RViz同时显示：

- `/lio_ob/tracking_path`；
- `/lio_ob/local_plan`；
- `/lio_ob/obstacles`；
- `/lio_ob/keepout_map`；
- 车辆当前位姿。

重点确认车辆是否处于parking路径点1至点4，以及 `progress_index` 是否接近该短前进段。

### P1：增加可观测性

当前日志应优先改进为同时打印：

- `障碍点数`，替代容易误解的“候选点”；
- 实际生成轨迹数；
- 当前路径点和同方向段终点索引；
- 同方向剩余弧长；
- 本轮使用的走廊半宽；
- 每条失败轨迹首次越界的推演距离和最大路径偏差；
- 被拒绝轨迹的RViz颜色标记。

这些改动只增加诊断信息，不改变控制行为。

### P2：针对短前进段/换向点设计专门策略

最合理的长期修复不是无条件增大走廊，而是识别：

```text
当前同方向剩余路径远短于局部规划推演距离
并且前方已经出现障碍
```

此时应安全制动，并判断能否提前进入路线本来就计划执行的倒车段，而不是继续要求生成1.80 m的前进避障轨迹。该策略必须检查倒车方向安全，不能只修改方向标志后立即倒车。

另一个可选方案是重新设计扫码后的parking接入路径，删除或延长只有0.116 m的前进短段，避免局部规划器刚接管就遇到硬换向边界。

### P3：参数A/B测试，只用于验证假设

可单独测试以下参数，但每次只改一个：

1. 临时减小 `local_plan_horizon`，验证是否确由1.80 m推演跨过短方向段导致；
2. 在RViz确认场界余量后，小幅增大 `emergency_path_half_width`，验证走廊是否过紧；
3. 增加曲率样本不能解决“所有轨迹必然离开短路径段”的结构性问题，只能改善采样稀疏；
4. 修改 `weight_*` 对本次无效，因为权重只作用于已经通过硬检查的轨迹；
5. 增大 `local_path_window` 也不一定有效，因为 `direction_segment_end()` 仍禁止前进轨迹匹配后续倒车段。

不建议直接取消路径走廊或关闭碰撞检查。照片中的空地是人眼判断，控制器还需要面对定位误差、车体包络、转向滞后和雷达盲区。

## 7. 最终判断

本次现象属于“**自由空间存在，但当前轨迹模型与路径走廊约束无法表达这条通路**”，不是雷达认为所有方向都会撞锥桶。

证据链为：

```text
30 = 确认并记忆的激光障碍点数，不是轨迹数
17 = 15个曲率样本 + 追踪曲率 + 视觉曲率
路径走廊=17 = 所有轨迹全部在走廊检查处失败
角速度/路径指标/禁行区/碰撞均为0 = 不是这些项目直接淘汰
parking开头同方向段仅约0.116 m，而轨迹推演1.80 m
路径距离搜索禁止跨越前进→倒车换向点
```

因此，优化优先级应是：先验证当前路径点和同方向剩余长度，再为短方向段/换向点增加专门处理；不要首先调整碰撞半径、软代价权重或雷达滤波参数。
