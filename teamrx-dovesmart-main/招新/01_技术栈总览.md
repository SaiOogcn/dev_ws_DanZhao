# 睿行·DoveSmart 技术栈总览

> 用途：负责人自己复盘 + 给新队员讲「我们要做的是一个什么东西」。
> 内容依据是本届实际交付的代码与文档，不是理想架构。

## 一句话概括

在 **RDK X5** 上跑一套 **ROS 2（TROS）** 系统：摄像头负责「看清路和牌子」，
激光雷达加 IMU 加轮速负责「知道自己在哪里」，两者的结果交给一套会**分阶段交接控制权**
的控制器，最终驱动一台**阿克曼转向小车**，全自动按顺序完成四项子任务。

## 一、硬件清单

| 部件 | 型号 / 规格 | 在我们的系统里干什么 |
| --- | --- | --- |
| 主控 | RDK X5（地瓜机器人），Ubuntu 22.04 + TROS | 跑全部 ROS 2 节点、YOLO 推理、路径跟踪 |
| 底盘下位机 | STM32（串口通信） | 收速度/转角指令，回传轮速与 IMU 原始数据 |
| 车体 | 阿克曼转向小车 | 前轮转向 + 后轮驱动 |
| 前置摄像头 | USB 摄像头，1920 × 1080 | 巡线、障碍物检测、二维码识别 |
| 车尾深度相机 | 光鉴 Aurora 930（RGB-D） | 任务区对准图文标记牌取景；环形区测距纠偏 |
| 激光雷达 | 轮趣 N10（单线 TOF） | 定位的几何观测，以及避障的碰撞检查 |
| IMU | MPU6050（20 Hz） | 角速度预测、静止零偏标定 |
| 屏幕 | HDMI / DP 外接屏 | 显示二维码数字、行驶方向、图生文结果 |

## 二、软件分层

```text
┌─────────────────────────── 任务层 ───────────────────────────┐
│ 扫码状态机（控制权仲裁）→ 选顺/逆时针路线 → 到达 P 点停车     │
├────────────────────────── 决策与控制层 ──────────────────────┤
│ origincar_control           ：巡线 + HAT 避障 + 扫码对准      │

│ robot_localization EKF ：轮速 + IMU 融合出 /odom             │
├─────────────────────────── 感知层 ───────────────────────────┤
```

代码分布：`src/` 下 31 个功能包，自研与移植源码约 4.8 万行
（不含厂商预编译库），其中 `lio_hybird` 一个包就有 8411 行，
`pure_pursuit_node.cpp` 单文件 20.8 万字节。

## 三、六个技术模块（按数据流看）

### 1. 底盘与状态估计

- **做什么**：把「速度 + 转角」变成轮子上的动作，再把轮速和 IMU 读回来。
- **用什么**：`origincar_base` / `base_orin`（C++）+ 串口库 + `serial_ros2`。
- **关键点**：
  - 下位机走串口，指令是 `ackermann_msgs/AckermannDriveStamped`（转角 + 速度）；
  - IMU 原始数据经过四元数解算（`Quaternion_Solution.cpp`）再发布；
  - `robot_localization` 的 EKF 以 20 Hz、`two_d_mode` 融合 `/odom` 与 `/imu/data`，
    发布 `odom -> base_footprint`；
  - **同一个子坐标系只能有一个父节点**——这是我们后来把 LIO 的 `publish_tf` 关掉的原因。
- **量级**：`base_orin` 包约 916 行。

### 2. 视觉感知

两个完全不同的路子，各管一段：

- **传统图像处理**（`image_binary`，1072 行）：HSV 阈值切出黄色通道和绿色边界，
  开运算去噪、闭运算补洞、按连通域面积过滤。文件头有一整块
  「调试参数集中定义区域」，现场调阈值只需要改这一块。
- **深度学习**（`dnn_node_example` + 自训练 YOLOv8）：模型 `pro_03.bin`，
  4 个类别 `P` / `code` / `hat` / `line`，部署到 RDK X5 的 BPU 上推理，
  结果发布到 `/win_detection`（`ai_msgs/PerceptionTargets`）。

> 一个真实的坑：`image_binary.cpp` 里变量名 `GREEN_H_*` 其实存的是**黄色**阈值
> （8~40），`YELLOW_H_*` 存的是**绿色**阈值（90~140）。注释写对了，名字起反了。

### 3. 二维码识别

主备两条链路，输出语义完全一致（`/qr_code_result` 与 `/sign_switch`）：

- `qr_code_detection`：YOLO 先框出 `code` 目标，再用 OpenCV 的 WeChatQRCode 解码；
- `zxing_qr_code_detection`：基于 ZXing-C++，直接用原始图像解码（319 行，较轻）。

约定：二维码尾号**奇数** → `sign_data=3` 顺时针；**偶数** → `sign_data=4` 逆时针。

### 4. 定位（这届最有技术含量的一块）

`submap_lio_node.cpp`（6.5 万字节），一句话：**用轮速和 IMU 做预测，
用激光雷达做修正**。

```text
/imu/data  -> 平面运动预测 -------------------------------+
/odom 轮速 -> 纵向速度观测 -------------------------------+--> /lio_hybird/odom
/scan -> 去畸变 -> 关键帧 NDT 子地图 -> 迭代位姿更新 -----+
                        +-> 启动 / 被拒时回退 scan-to-scan ICP
```

- EKF 状态只有 5 个：`[x, y, yaw, 纵向速度, 陀螺零偏]`，刻意不做 3D；
- 只用轮速的**实测纵向速度**，不用它积分出来的位姿（避免同一个信息被用两次）；
- 默认**不融合** IMU 的四元数——车上 Madgwick 设了 `use_mag=false`，
  那个 yaw 本质是同一路陀螺的另一次积分，当独立观测会造成「双重计数」；
- 扫描按位移 0.20 m 或转角 30° 存成关键帧，体素 0.20 m，NDT 最多迭代 20 次。

### 5. 决策与控制

**（1）第一赛段：`origincar_control`（1010 行，C++）**

| 功能 | 做法 | 关键参数 |
| --- | --- | --- |
| 巡线 | 直接比例控制 | `angular.z = -(line_x - 920) × 0.0016` |
| 避障绕行 | 按包围框高度比触发，往帽子的侧向让开 | 正常 0.22 / 强制 0.50，目标 = 帽中心 + 1.60 × 侧别 × 帽宽 |
| 二维码对准 | 单独一套 PID | 置信度阈值 0.70 |
| 速度 | 三档工况 | 冲 1.20 / 常规 0.90 m/s |

**（2）下半场：`pure_pursuit_node.cpp`（20.8 万字节）**

- **纯追踪**：从当前位置往前找前瞻点，按曲率受限的方式追；
- **方向是硬语义**：路径 CSV 第八列写 1（前进）或 -1（倒车），
  换向点不可跨越，换向前按制动距离锁存停车；
- **局部避障**：视觉定绕行侧、雷达只做碰撞否决。候选轨迹是
  「转出 → 直行 → 转回」的固定三段曲率轮廓，当前参数下共 17 条
  （15 个均匀曲率 + 追踪曲率 + 视觉曲率）；
- **障碍点确认**：相邻束聚成 3 点簇 + 0.30 s 与 0.10 m 内二次观测，
  未确认的点 0.35 s 过期且永不参与碰撞检查；
- **脱困**：`ESCAPE_BRAKING -> ESCAPE_TRAJECTORY_SELECTED -> ESCAPE_REVERSING
  -> 制动稳定 -> ESCAPE_REPLAN`，最多两次，走完 0.30 m 才重置预算。

**（3）控制权仲裁**（我们最该讲给新人听的一个设计）

```text
扫码前：origincar_control 直接发 /cmd_vel，LIO 只定位不发速度
   │
   ├─ 收到有效 /sign_switch
   ▼
立即停图像订阅 → 发一次零速 → ack control_released
   │
   ├─ 底盘 /odom 实测速度 < 0.04 m/s
   ▼
所有权永久移交给 lio_hybird_controller（此后由它独占 /cmd_vel）
```

这条链的价值：把「两个节点抢底盘」这个**时序问题**变成了可以从
`/lio_hybird/state` 读出来的**状态问题**。

### 6. 交互与展示

- 车端 `ring_photo_client` 取一帧车尾图 → 旋转 180° → 缩放到 512 × 512 →
  JPEG 质量 60 编码 → ZMQ `tcp://<PC_IP>:5555` 发给 PC；
- PC 上的视觉大模型生成中文描述后回传 → `/take_photo/result`；
- `qr_screen_display` 统一订阅二维码、方向、描述，显示在车载屏幕上；
- 上传与轮询放在独立线程，带重试和退避，**网络异常不影响控制环**。

| 环节 | 工具 | 说明 |

## 六、这届留下的技术债（下一届优先改）

1. **版本管理几乎为空**：工作区 git 到赛后仍无任何提交，关键实验包未被跟踪，
   无法回滚也说不清「哪一版跑出过好结果」。
2. **规划器表达力不足**：局部轨迹只有固定三段曲率轮廓，在短方向段和换向点附近
   结构性失效（8 月 7 日那次 17 条轨迹全被走廊拒绝就是这个原因）。
3. **可观测性补得晚**：拒绝原因计数、障碍点数这些诊断信息是出事之后才补的。
4. **并行实验包太多**：`lio_hybird` / `lio_ob` / `lio_aurora` 三个高度重叠的包，
   路线族 20 余份，现场靠参数和记忆选，容易选错。
5. **参数与代码耦合**：改一个阈值要重编整个包，容易跑在旧二进制上。
